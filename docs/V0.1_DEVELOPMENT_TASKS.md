# ShotMill V0.1 第一版开发任务

> 状态：开发基线  
> 版本目标：V0.1  
> 仓库：https://github.com/terry-xu-2077/TerryShotMill  
> 关联文档：`ShotMill_产品与架构规划.md`、`UI_UX_SPEC.md`、`TEST_STRATEGY.md`

本文档用于把 ShotMill 第一版拆成可直接交给 Codex 以“目标”方式执行的开发任务。

V0.1 的目标不是一次做成完整成熟产品，而是建立一个**架构正确、UI 手感可打磨、核心链路完整、能够真实批量生产视频素材、后续可持续扩展**的第一版。

---

## 1. V0.1 最终必须跑通的闭环

```text
创建 / 打开项目
    ↓
导入项目资产
    ↓
连续创建一批 Task
    ↓
选择 / 继承资产
    ↓
Prompt AI Provider 编写 Prompt
    ↓
人工检查 / 修改 Final Prompt
    ↓
Ready Validation
    ↓
批量加入 Queue
    ↓
Video Generation Provider 执行
    ↓
查看进度
    ↓
结果回收
    ↓
通过 / 编辑 / 重生成 / 设为 Primary
    ↓
导出已通过素材
```

同时至少支持一条：

```text
Task A → Task B
```

的上下文连续生成链路。

V0.1 完成后，用户应可以真正拿它完成一次短剧素材生产，而不是只能展示 UI 或跑单个 Demo。

---

## 2. V0.1 明确不做

第一版不扩展到以下范围：

- 视频剪辑时间线。
- 多轨编辑。
- 转场 / 字幕 / 配音编辑器。
- 自动成片。
- 云端账号体系。
- 多人协作。
- 完整插件市场。
- 原生手机 App。
- 多机分布式渲染调度。
- 复杂权限系统。
- 所有未来 Provider 的完整实现。

V0.1 只要求 Provider 架构可扩展，并实现首批必要 Adapter。

## 4. 开发总原则

第一版必须遵守以下顺序：

```text
基础工程与测试
    ↓
/dev/ui + Mock UI
    ↓
用户打磨 UI 手感
    ↓
冻结第一轮核心交互
    ↓
Core / Database / Provider / Scheduler
    ↓
Fake Provider 全链路
    ↓
真实 Prompt Provider
    ↓
真实 Video Provider / ComfyUI
    ↓
UI 接真实 Backend
    ↓
Remote Monitor
    ↓
完整回归 / Hardware Smoke
```

**不得一开始就把真实后端和复杂 UI 强耦合。**

UI 可见体验由用户在 `/dev/ui` 中集中打磨；不可见业务逻辑由 Codex + 自动测试闭环完成。

# Phase 4 — Queue / Scheduler / Ready Validation

这是后端第一版最关键的模块之一。

## T4.1 Ready Validator

分两层：

```text
Generic Validation
Provider / Generation Profile Validation
```

检查：

- final_prompt。
- assets。
- provider profile。
- generation profile。
- params。
- context dependency。

---

## T4.2 Queue Model

支持：

- enqueue。
- dequeue。
- priority。
- pause。
- resume。
- cancel。
- retry。

第一版可先实现单个主 Queue Lane，但数据模型不得阻止未来多 Lane。

---

## T4.3 DAG Scheduler

支持：

```text
A → B → C
D → E
F
```

规则：

- 无依赖 Task 可并行进入 Ready / Queue。
- 下游等待上游成功。
- 上游失败只阻塞 dependents。
- 不阻塞其他独立 Task。

---

## T4.4 Crash Recovery

必须支持：

- ShotMill 退出后恢复。
- Provider 断开。
- Running Job 重连 / reconcile。
- remote job 丢失。
- duplicate event。

---

## T4.5 Context Stale

上游 Primary Result 变化时：

- 下游已有 Result 不删除。
- 下游标记 Context Stale。
- 用户决定是否重新生成。

### Gate 4

用 FakeVideoProvider 自动执行至少 50 个 Task + 多条 DAG，并完成 Failure Scenarios 回归。

# 5. V0.1 Definition of Done

第一版只有满足以下条件才算完成：

1. 可以创建并打开独立 Project。
2. Asset 可导入并在 Task 间复用。
3. 可以高效连续创建几十个 Task。
4. Prompt Provider 可替换，至少一个真实 API Provider 可用。
5. Final Prompt 与 AI Prompt 分离且人工修改不会被自动覆盖。
6. Video Generation Provider 可替换，ComfyUI Adapter 可用。
7. MiniMax-H3 可作为首个真实 Generation Profile 完成生成。
8. Task / Job / Result 分离，Result 历史不被重生成覆盖。
9. Queue 支持批量生成、暂停、恢复、重试、取消。
10. Scheduler 支持 Task Chain 依赖。
11. 应用 / Provider 中断后具备合理恢复能力。
12. 至少一种真实 Task Context 连续生成方式可用。
13. Primary Result / Context Stale 工作正确。
14. Result Review 可快速通过 / 重生成 / 编辑。
15. 可导出已通过结果。
16. `/dev/ui` 长期保留并覆盖主要 UI 状态。
17. 核心 UI 有 Playwright + Visual Regression。
18. Provider 有 Contract Tests。
19. Scheduler / Recovery 有 Integration Tests + Failure Injection。
20. 手机端可查看真实进度并进行轻量审核。
21. `python scripts/verify.py --full` 通过。
22. 真实 Hardware Smoke 通过。

# 6. 建议的 Codex 目标粒度

不要给 Codex：

```text
完成整个 Task 系统
```

而应拆成能独立验收的目标，例如：

```text
目标：实现 Task Domain Model 的 create / copy / insert / reorder。
遵循 ShotMill_产品与架构规划.md。
增加对应 unit tests。
不要实现 UI 或 Provider。
完成后运行 python scripts/verify.py --area backend。
```

UI 目标示例：

```text
目标：在 /dev/ui 中实现 TaskCard 的 Draft、Ready、Running、Failed、Context Stale 五种状态。
严格遵循 UI_UX_SPEC.md。
只使用 Mock 数据，不连接真实 Backend。
补 Playwright 交互测试和视觉回归。
```

Bug 目标示例：

```text
目标：修复应用重启后 Running Job 永久停留在 Running 的问题。
先增加可复现该问题的 integration test，确认失败后再修复。
不得删除或弱化已有测试。
完成后运行 scheduler targeted verification。
```

# 7. 推荐开发节奏

第一版不要同时打开过多并行目标。

推荐：

```text
一个领域基础设施目标
        ↓
一个可测试业务目标
        ↓
自动验收
        ↓
合并 / 固化
        ↓
下一个目标
```

UI 阶段可以更集中：

```text
Codex 做 Mock UI
↓
用户体验
↓
集中修改手感
↓
确认
↓
加自动回归
↓
再进入下一块 UI
```

后端阶段则尽量做到：

```text
用户只定义行为
↓
Codex 实现 + 测试 + 修复
↓
机器验收
↓
只有架构决策或最终真实体验才需要人工介入
```

## 9. 第一版开发的核心判断标准

如果开发过程中必须在“功能更多”和“主链路更稳定”之间选择，V0.1 一律优先后者。

如果必须在“多支持一个模型”和“Provider Contract 更干净”之间选择，优先 Contract。

如果必须在“UI 功能更多”和“高频操作更顺手”之间选择，优先手感。

如果必须在“快速临时修好”和“留下可回归的修复”之间选择，优先回归测试。

ShotMill V0.1 的成功标准不是功能列表长度，而是：

> **用户可以舒适地准备一批任务，放心点击批量生成，离开电脑，回来快速审核和局部返工；与此同时，系统核心没有被当前 H3、ComfyUI 或某个 Prompt 模型锁死。**
