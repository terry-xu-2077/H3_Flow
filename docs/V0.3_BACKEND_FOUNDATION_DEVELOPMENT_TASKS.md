# ShotMill V0.3 Backend Foundation 开发任务

> 状态：规划 / 待实施  
> 版本目标：V0.3 — Backend Foundation  
> 最后修订：2026-09-13  
> 前置版本：`V0.2_STORYBOARD_DEVELOPMENT_TASKS.md`  
> 关联文档：`AI_PROMPT_ENHANCEMENT_ARCHITECTURE.md`、`V0.5_BACKEND_FRONTEND_ADAPTER.md`、`V0.6_BACKEND_DELTA.md`、`STORYBOARD_TASK_MODEL.md`、`TEST_STRATEGY.md`

本文档是 ShotMill **V0.3 的主开发执行清单**。

V0.3 的目标不是继续扩展 UI 功能，而是把已经在 V0.1 / V0.2、当前 Director UI 与后续架构文档中确定的领域边界，真正落到后端代码中。

当前后端只有 FastAPI / CORS / `/health` 基础壳，因此这轮更准确地说是 **正式后端架构落地**，不是昂贵的旧系统重构。

---

# 1. V0.3 核心目标

完成一个可长期演进的 **模块化单体后端基础**：

```text
React / Tauri
    ↓
Frontend Adapter / Read Model
    ↓
Application Services
    ↓
Domain
    ↓
Repository / SQLite
    ↓
Prompt AI Provider / Video Generation Provider
```

V0.3 完成后，前端不再以 Mock `GenerationTask` JSON 作为真实数据源，而是通过稳定的 Gateway / API 消费后端 Read Model。

### V0.3 必须达到

- Project / Asset / Task 成为正式后端领域对象；
- SQLite 持久化与 Repository 边界建立；
- Frontend Adapter / Read Model 真正落地；
- 当前“项目首页 → 项目工作台 → 任务编辑弹窗”可接真实后端；
- AI Prompt Enhancement 有正式 Application / Provider / Skill 接口；
- Job / Result 在接真实视频生成前建立不可变快照模型；
- 后端保持 Provider / Model 无关，不绑定 H3、Qwen 或 ComfyUI；
- 测试从 health-only 升级为 Domain / Repository / API / Contract 基础覆盖。

---

# 2. V0.3 明确不做

本版本不要过度架构。

明确不引入：

- 微服务；
- Redis；
- Celery；
- Kafka / 消息总线基础设施；
- Event Sourcing；
- CQRS 框架；
- GraphQL；
- 为了“未来可能需要”提前拆独立 AI 服务；
- 为了远程 GPU 提前拆独立生成服务；
- 分布式数据库。

当前推荐形态：

```text
FastAPI 模块化单体
+ SQLite
+ SQLAlchemy 2.x
+ Alembic
+ Provider Adapter
```

未来需要远程执行时，优先拆 **Provider 执行层**，不是拆 Domain。

# Phase B0 — Backend Skeleton

目标：先建立不会被后续功能推翻的模块边界。

## B0.1 FastAPI Router 化

- `/` 与 `/health` 保留；
- API 统一前缀 `/api/v1`；
- `app.py` 只负责应用组装、middleware、lifespan、router 注册；
- 业务逻辑不得直接写在 route handler 中。

## B0.2 依赖管理

加入并锁定第一阶段必要依赖：

- SQLAlchemy 2.x；
- Alembic；
- Pydantic / FastAPI 现有体系；
- SQLite driver 使用 Python 标准能力或 SQLAlchemy 默认方案。

暂不加入 Redis / Celery 等依赖。

## Gate B0

- 后端可启动；
- `/health` 继续通过；
- Router / Application / Domain / Persistence 目录职责建立；
- 无业务逻辑继续堆入 `app.py`。

# Phase B1 — SQLite + Repository Foundation

目标：建立 ShotMill Source of Truth 的正式存储基础。

## B1.1 数据库策略

第一阶段使用：

```text
SQLite + SQLAlchemy 2.x + Alembic
```

推荐项目目录：

```text
Project/
├─ project.db
├─ assets/
├─ thumbnails/
├─ outputs/
├─ context/
└─ cache/
```

业务对象使用稳定 ID 与 project-relative path，不传播绝对路径。

## B1.2 Repository 边界

至少建立：

```text
ProjectRepository
AssetRepository
TaskRepository
JobRepository
ResultRepository
PromptRevisionRepository
```

Application 层依赖 Repository 接口，不直接散落 SQL 查询。

## B1.3 Migration

- Alembic 初始化；
- 每次 schema 修改必须 migration；
- 禁止通过启动时“自动猜 schema”替代 migration。

## Gate B1

- 可以创建 / 打开项目数据库；
- migration 可从空库建立当前 schema；
- Repository unit/integration tests 覆盖基本 CRUD；
- 绝对文件路径不进入普通业务 API。

# Phase B2 — Project / Asset / Task Core

目标：先实现新前端真正依赖的三个核心对象。

## B2.1 Project

至少支持：

```text
id
title
description
use_description_for_ai_prompt
created_at
updated_at
```

项目配置 UI 可直接映射这些正式字段。

## B2.2 Asset

正式区分用户显示信息与原始文件信息：

```text
Asset
├─ id
├─ name                  # 用户可编辑显示名，@ 菜单使用
├─ original_filename     # 只读
├─ project_relative_path # 业务存储
├─ media_type
├─ category
├─ tags
├─ width / height
├─ duration
├─ hash
└─ thumbnail_path
```

规则：

- 改 `name` 不修改原文件；
- `original_filename` 只读；
- 删除资产必须处理 Task Binding 悬空引用；
- 项目资产库存在 ≠ AI 增强自动发送该资产。

## B2.3 Task

Task 是可修改生产意图，至少保存：

```text
id / display order / title / summary
script_source / user_intent
user_prompt / ai_prompt / final_prompt
prompt_source
generation params
asset bindings
planned duration
story order / placement
primary_result_id?
```

Scene / TaskPlacement 可保留在内部 Domain；当前 UI 不显示 Scene 不代表删除它。

## Gate B2

- 项目可创建、重命名、修改简介；
- Asset 可导入、改显示名、编辑元数据、移除；
- Task 可新建、读取、编辑、排序；
- 新建任务只有点击“保存”才落库；
- Prompt Source 的 user / ai 两份数据独立保存。

# Phase B3 — Frontend Adapter / Read Model

目标：让新 UI 接真实后端时不理解 Core 内部复杂度。

长期遵循 `V0.5_BACKEND_FRONTEND_ADAPTER.md`。

至少实现：

```text
ProjectSummary
ProjectWorkspaceView
TaskSummary
TaskEditorView
ProjectRuntimeSummary
```

## B3.1 首页

```http
GET  /api/v1/projects
POST /api/v1/projects
PATCH /api/v1/projects/{project_id}
```

首页不得为了项目卡加载完整 Task / Result / Asset 对象。

## B3.2 项目工作台

```http
GET /api/v1/projects/{project_id}/workspace
```

聚合：

- 项目标题；
- TaskSummary[]；
- 当前运行摘要。

Project status、Task status、resultCount、preview fallback 等由 Adapter 计算，不丢给 React。

## B3.3 任务编辑

```http
GET   /api/v1/projects/{project_id}/tasks/{task_id}/editor
POST  /api/v1/projects/{project_id}/tasks
PATCH /api/v1/projects/{project_id}/tasks/{task_id}
```

UI 不直接消费完整 `GenerationTask`。

## B3.4 Frontend Gateway

前端建立正式 `ProjectGateway`，逐步替换组件中的临时 `fetch()` 和 Mock Repository。

## Gate B3

- 项目首页可由真实 API 驱动；
- 项目页列表 / 卡片消费同一 Read Model；
- 右侧只读栏不需要理解 Job / Result / Context；
- 任务编辑窗通过 `TaskEditorView` 加载 / 保存；
- React 不直接依赖数据库 schema。

# Phase B4 — AI Prompt Enhancement Foundation

目标：按 `AI_PROMPT_ENHANCEMENT_ARCHITECTURE.md` 实现真正的多模态 Prompt Enhancement 子系统。

## B4.1 Application Service

建立 `PromptEnhancementService`，负责：

- 读取当前 Task；
- 解析当前真正绑定的 Asset；
- 根据用户开关读取可选项目背景；
- 根据用户开关读取可选上一任务摘要；
- 选择目标 Prompt Skill；
- 调用 Prompt AI Provider；
- 保存独立 revision。

## B4.2 输入规则

核心输入：

```text
用户描述
+ 当前任务实际图片 / 视频
+ 媒体角色
+ 可选项目背景
+ 可选上一任务摘要
+ 必要生成约束
```

禁止：

- 用 Asset 名称代替真实媒体；
- 默认发送上一任务完整 Prompt；
- `includePreviousTaskSummary=false` 仍发送摘要；
- 因资产存在于项目库就自动上传；
- 在 React 中处理绝对路径 / base64 / provider 上传逻辑。

## B4.3 Prompt Skill

至少预留：

```text
MiniMax H3 Prompt Skill
Seedance 2.0 Prompt Skill
```

二者可共用 Prompt AI Provider，但不能共用一套混杂 System Prompt。

## B4.4 Provider Adapter

Provider Capability 决定：

- image input；
- native video input；
- sampled video frames；
- audio understanding；
- system prompt；
- structured output。

Provider Adapter 负责 URL 上传、base64、`image_url / video_url`、视频抽帧降级等媒体传输细节。

## B4.5 AiPromptRevision

每次增强创建独立 revision，至少记录：

```text
id / task_id / created_at
source_user_prompt
output_prompt
asset_ids
project_background_used
previous_task_summary_used
skill_id / skill_version
provider_profile_id / model
```

失败调用不创建伪 revision。

## Gate B4

- 同一 Task 可产生多个 AI Prompt Revision；
- 用户可切换历史版本；
- 项目背景与上一任务摘要均是独立可选上下文；
- 实际图片 / 视频真正进入多模态 Provider；
- H3 / Seedance Skill 边界成立；
- Prompt Provider 可被替换而不修改 Task Domain。

# Phase B5 — Job / Result Foundation

目标：在正式接视频生成 Provider 前，先建立不可变执行历史。

## B5.1 Job

Task 是可变的，Job 是一次生成提交的不可变快照。

Job 至少冻结：

- final prompt；
- Asset Binding；
- Generation Profile / Provider Profile；
- provider-specific params；
- seed（若支持）；
- Context 来源；
- 提交时间；
- 状态 / 错误。

后续修改 Task 不得静默修改历史 Job。

## B5.2 Result

- Result 属于 Job；
- 一个 Task 可有多个历史 Result；
- Primary Result 是 Task 当前选中的结果；
- 新生成不能覆盖旧 Result；
- Result 预览 / 播放信息由 Frontend Adapter 输出。

## Gate B5

- 连续生成多个版本后历史可追溯；
- 修改 Prompt / Asset 后旧 Job Snapshot 不变；
- TaskSummary 能正确计算 resultCount / preview；
- Primary Result 切换不删除历史。

# Phase B6 — Video Generation Provider / ComfyUI

目标：在 Domain、Job、Result 稳定后再接第一个真实执行端。

第一阶段重点 Adapter：

```text
Video Generation Provider: ComfyUI
Model / Generation Profile: MiniMax H3
```

但 Core 不允许出现：

```text
if provider == comfyui
if model == h3
```

专属逻辑必须位于：

- Provider Adapter；
- Generation Profile；
- Capability；
- Prompt Skill；
- Validator。

## B6.1 ComfyUI Adapter

负责：

- workflow / prompt 构造；
- 提交；
- queue / progress 查询；
- result 回收；
- provider error 归一化。

## B6.2 Capability

至少表达：

- text / image / first frame / last frame；
- reference images / videos；
- max duration；
- continuation / visual context；
- progress reporting；
- batch / concurrency。

## Gate B6

- 一个 Ready Task 可以创建 Job 并提交到 ComfyUI；
- ComfyUI 返回结果后创建 Result；
- Provider 故障不会破坏 Task 数据；
- 替换 Provider 不需要修改 Core Domain。

---

# Phase B7 — Runtime Events / Queue Basics

目标：支撑项目页实时状态和后续手机进度页。

优先采用项目级 SSE：

```http
GET /api/v1/projects/{project_id}/events
```

事件至少考虑：

```text
task.status_changed
task.progress_changed
task.result_added
project.runtime_changed
project.summary_changed
```

第一阶段允许轮询 fallback，但 Application / Repository 不应与轮询实现绑死。

V0.3 不要求复杂分布式 Queue；先实现单机可追踪队列与并发限制。

## Gate B7

- 项目页底部运行状态可实时更新；
- Task 卡 / 列表状态可增量更新；
- 事件模型可被未来移动端进度页复用。

# 4. 开发优先级

```text
P0
├─ B0 Backend Skeleton
├─ B1 SQLite + Repository
├─ B2 Project / Asset / Task
└─ B3 Frontend Adapter

P1
├─ B4 AI Prompt Enhancement
├─ B5 Job / Result
└─ B6 ComfyUI Provider

P2
└─ B7 Runtime Events / Queue Basics
```

**不要在 B0-B3 未稳定时，把真实 ComfyUI workflow、Prompt AI Provider 或 Queue 逻辑直接绑进 React。**

# 7. V0.3 之后

V0.3 完成后，再进入更高层能力，例如：

- 更完整的 Task Chain / Context Stale；
- 批量调度与失败重试策略；
- 手机端远程进度页面；
- 多 Video Provider；
- 多 Prompt AI Provider Profile；
- Provider 配置 UI；
- 复杂任务依赖图；
- 更强的连续片段生成。

这些功能都应建立在 V0.3 的 Domain / Repository / Adapter / Job 基础上，而不是绕过它们直接堆到前端或 Provider 代码里。
