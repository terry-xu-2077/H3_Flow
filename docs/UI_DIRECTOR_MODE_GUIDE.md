# ShotMill Director Mode UI 开发规范

> 状态：V0.3 起强制执行  
> 最后更新：2026-09-13  
> 适用范围：Desktop UI、`/dev/ui`、后续移动端工作流  
> 优先级：本规范是 `UI_UX_SPEC.md` 的产品信息架构补充；涉及“哪些信息可以出现在首屏”时，以本规范为准。

## 0. 为什么新增这份规范

V0.2 已经证明 ShotMill 的领域模型和生产能力可以支撑复杂工作流，但前端曾把过多内部概念同时暴露给用户：Scene Navigator、Task Board、Inspector、Profile、Visual Beat、Context Link、Ready Validation、Job、Result、Provider 等在同一个工作区出现，导致视觉密度和学习成本快速上升。

从 V0.3 开始，ShotMill 的 UI 目标正式调整为：

> **能力保持完整，默认界面只暴露完成当前创作动作所需的信息。**

ShotMill 不是“AI 参数控制台”，也不是“后端领域模型查看器”。

用户的主心智必须稳定在：

```text
剧本 → 故事板 → 生成 → 看结果 / 局部返工
```

内部实现仍可使用 `GenerationTask`、`TaskVisualBeat`、`GenerationContextLink`、`Job`、`Result`、`GenerationProfile` 等对象，但这些名字和字段默认不得直接成为主界面信息架构。

---

## 1. Director Mode 的一级信息架构

桌面端一级导航固定围绕三个工作目标：

1. **故事板**：创建、排列、查看、快速编辑分镜。
2. **生成**：查看生成队列、进度、失败与重试。
3. **素材**：集中管理角色、场景、道具、参考图、视频、音频。

以下内容不得占用一级导航：

- Result Review：结果应回到对应分镜 / 生成记录中查看；若后续需要独立审核墙，只能作为生成页的二级视图。
- Project Settings：放在右上角设置入口。
- Provider / Model / Profile 管理：放在设置或高级设置。
- Prompt 管理：属于单个分镜的高级编辑。

### 1.1 禁止重复工作区

同一个业务对象不能在两个一级页面同时提供完整编辑能力。

**故事板是唯一的分镜编辑入口。**

生成页只能：

- 看等待 / 运行 / 完成 / 失败状态；
- 看进度；
- 暂停、取消、重试（后端支持后）；
- 定位回对应分镜。

生成页不得再次提供：

- 新建分镜；
- 修改分镜描述；
- 修改素材；
- 修改 Profile；
- 修改 Prompt；
- 复制 / 批量编辑分镜内容。

## 2. 参数暴露预算（强制）

这是防止再次出现“参数堆砌 UI”的核心规则。

### 2.1 首屏预算

用户进入任意一级工作区后，**无需点击展开、详情、高级设置**即可看到的可交互参数，应满足：

- 故事板首屏：每张分镜卡最多显示 **5 类信息**。
- 分镜简单详情：最多显示 **4 个主要编辑区**。
- 生成队列行：最多显示 **4 类状态信息**。
- 素材卡：最多显示 **4 类信息**。

如果超过预算，必须合并、隐藏、延后展示，而不是缩小字号继续塞。

### 2.2 分镜卡固定信息层级

默认分镜卡只允许显示：

1. 代表画面 / 结果预览；
2. 分镜编号；
3. 一句话标题或描述；
4. 计划时长；
5. 用户可理解的生成状态。

默认不得显示：

- Generation Profile 名称；
- Asset 数量；
- Visual Beat 数量；
- Prompt 状态细节；
- Context Link 类型；
- Job ID / Result ID；
- Provider 名；
- Capability；
- Validation 项数；
- 内部稳定 ID。

以上信息只有在它会改变用户当前决策时，才可进入二级 / 三级界面。

### 2.3 简单详情固定结构

用户显式打开一个分镜后，第一层详情只允许出现：

```text
代表画面
画面描述
时长
素材
连续性摘要
[生成视频]
[高级设置 >]
```

其中“连续性摘要”必须翻译成用户语言，例如：

- `已自动衔接上一分镜`
- `上一分镜已修改，建议重新同步`
- `独立起始分镜`

禁止在第一层详情直接出现：

- Context Link ID；
- semantic / visual / latent / native 等内部 Context Kind；
- Generation Profile Capability；
- AI Prompt Revision；
- Final Prompt；
- Visual Beat 参数表；
- Generation Params JSON；
- Job Snapshot；
- Result Metadata。

这些内容统一进入“高级设置”。

## 3. Progressive Disclosure：三级信息结构

任何复杂能力都必须先判断属于哪一级。

### Level 1：故事板 / 队列首屏

回答三个问题：

- 现在有哪些画面？
- 哪些需要我处理？
- 下一步可以做什么？

### Level 2：简单详情

回答：

- 这个分镜讲什么？
- 多长？
- 用哪些素材？
- 和上一分镜是否连续？
- 能否生成？

### Level 3：高级设置

只有明确需要精细控制的用户才进入：

- Script Source；
- User Intent；
- AI Prompt / Final Prompt；
- Visual Beats；
- Generation Profile；
- Provider-specific Params；
- Context 调试；
- 历史 Prompt Revision / Job / Result；
- Capability / Validation 细节。

**禁止把 Level 3 字段为了“方便”搬回 Level 1。**

如果高级能力使用频率变高，应优化 Level 2 的动作语义，而不是直接把高级字段平铺出来。

---

## 4. 用户术语与内部术语隔离

UI 默认使用创作语言，而不是工程语言。

| 内部术语 | 默认用户术语 | 允许直接显示的位置 |
| --- | --- | --- |
| GenerationTask | 分镜 / 片段 | 高级调试页可显示 Task |
| TaskVisualBeat | 内部镜头 / 镜头段落 | 高级设置 |
| GenerationContextLink | 连续性 | 高级调试页 |
| Context Stale | 连续性需同步 | 状态提示 |
| GenerationProfile | 生成方案 | 高级设置 |
| Ready Validation | 生成前检查 | 仅失败时展开 |
| Job | 生成记录 | 生成历史 |
| Result | 生成结果 | 可显示 |
| Provider | 生成服务 | 设置 / 状态栏 |
| Prompt Revision | 提示词版本 | 高级设置 |

禁止在普通界面混合出现大量中英文工程词，例如：

`Task / Beats / Context / Profile / Ready / Provider / Result / Job`

开发模式和测试可使用内部术语，但产品 UI 文案必须使用用户术语。

---

## 5. 故事板布局规则

### 5.1 默认必须是单主画布

V0.3 默认故事板结构：

```text
页面标题 + 少量全局动作
────────────────────────
场景 01
[分镜] [分镜] [分镜] [+]

场景 02
[分镜] [分镜] [+]
```

禁止默认恢复 V0.2 的：

```text
Scene Navigator | Task Board | Inspector
```

三栏并列结构。

场景导航、批量属性、技术 Inspector 等只能按需出现，不能常驻抢占画布宽度。

### 5.2 图像优先

分镜卡视觉权重从高到低：

1. 代表画面；
2. 标题 / 一句话描述；
3. 状态；
4. 时长；
5. 其他信息（默认不显示）。

如果 UI 装饰、标签或状态块抢过了缩略图的注意力，视为设计失败。

### 5.3 不用缩小字号解决拥挤

当信息放不下时，处理顺序必须是：

1. 删除不必要信息；
2. 合并语义；
3. 延迟到详情；
4. 改成 Tooltip / Popover；
5. 最后才考虑布局尺寸。

禁止通过：

- 8px 以下文字；
- 多行密集 key-value；
- 一排十几个 Pill；
- 四层折叠区同时展开；

来“容纳更多参数”。

## 6. 操作密度规则

### 6.1 一个区域只保留一个主动作

例如分镜详情：

- 主动作：`生成视频`
- 次动作：`高级设置`

不得同时并列：

`生成 Prompt / 验证 Ready / 更新 Context / 加入 Queue / 重新生成 / 保留 Result / 重编 Prompt`

这些是系统步骤或高级动作，应由流程自动化或高级界面承载。

### 6.2 系统可推导的步骤不得要求用户逐项确认

如果系统可以安全判断：

- 当前 Profile；
- 是否需要继承上一分镜；
- 是否需要做 Ready Validation；
- Queue Job 快照；

则普通用户点击“生成视频”后，系统应自动执行必要检查。

只有遇到不能自动解决的问题时，才提示用户具体需要处理什么。

### 6.3 错误提示使用任务语言

禁止：

`ContextLink stale because source PrimaryResult changed`

应该：

`上一分镜的结果已经更换，请先同步连续性。`

禁止：

`Profile Capability multiShotPrompt=false`

应该：

`当前生成方案不支持一个片段中的多个镜头。`

---

## 7. 高级设置的边界

高级设置允许复杂，但仍然要分区，不得做成参数墙。

建议顺序：

1. 剧本与创作意图；
2. 内部镜头；
3. 素材引用；
4. 提示词；
5. 生成方案；
6. 连续性；
7. 历史版本 / 生成记录。

默认只展开当前任务最相关的 1–2 个区域。

Provider-specific 参数必须放在“生成方案 / 高级参数”内部，不能渗透到故事板卡片和简单详情。

---

## 8. 视觉风格约束

延续 `UI_UX_SPEC.md`：

- 深色、中性色、低饱和度为主；
- 高饱和色只用于选中、状态、警告、错误、关键动作；
- 不使用大面积 AI 紫蓝渐变；
- 不把每一个状态做成彩色 Badge；
- 卡片边框和背景层级要克制；
- 图片 / 视频内容必须成为画面视觉中心；
- 控件高度和间距优先保证可读性，不以“看起来专业”为理由压缩到难以点击。

---

## 9. 新功能进入 UI 前的强制审查

每增加一个前端字段、按钮、Badge、面板前，必须回答：

1. 用户当前正在完成什么动作？
2. 这个信息会改变用户此刻的决策吗？
3. 如果隐藏到详情，用户是否仍然能完成主流程？
4. 这是用户概念，还是内部实现概念？
5. 能否由系统自动推导？
6. 是否已经在另一个一级页面提供了同一编辑能力？

只要以下任一成立，默认不得放到首屏：

- “以后可能有用”；
- “后端本来就有这个字段”；
- “调试比较方便”；
- “这样信息更完整”；
- “高级用户也许会看”；
- “空着也是空着”。

---

## 10. Code Review / Codex 验收清单

涉及 UI 的 PR 必须检查：

- [ ] 一级导航是否仍然围绕故事板 / 生成 / 素材？
- [ ] 是否新建了重复的分镜编辑入口？
- [ ] 故事板默认是否仍是单主画布？
- [ ] 分镜卡是否超过 5 类信息？
- [ ] 简单详情是否出现 Profile / Prompt / VisualBeat / ContextLink / Job 等工程概念？
- [ ] 一个区域是否出现多个同等级主按钮？
- [ ] 是否通过缩小字号或增加 Badge 来解决信息过多？
- [ ] 系统可自动完成的步骤是否被暴露成手工流程？
- [ ] 错误文案是否使用用户语言？
- [ ] 高级设置是否仍然可访问，没有因为简化 UI 删除核心能力？
- [ ] `/dev/ui` 是否覆盖空项目、少量分镜、大量分镜、生成中、失败、连续性失效等状态？

任何一项失败，都应先调整信息架构，再讨论视觉微调。

## 11. 当前 V0.3 基线

V0.3 Director Mode 第一阶段采用：

```text
一级导航
├─ 故事板
├─ 生成
└─ 素材

故事板
├─ 场景分组
├─ 分镜卡
├─ 添加分镜
├─ 导入剧本
├─ 连续预览
└─ 简单分镜详情
   ├─ 画面描述
   ├─ 时长
   ├─ 素材
   ├─ 连续性摘要
   ├─ 生成视频
   └─ 高级设置

生成
├─ 等待
├─ 生成中
├─ 失败
└─ 已完成

高级设置
└─ 保留 V0.2 已完成的完整 Task / Prompt / Beat / Profile 能力
```

这意味着：

> **简化 UI 不等于删除能力；简化 UI 是把能力放到正确的层级。**
